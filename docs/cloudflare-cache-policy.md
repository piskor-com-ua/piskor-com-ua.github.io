# Cloudflare: місячний кеш і керована інвалідація

Вимога власника від 24.10.2026: кеш Cloudflare CDN усіх публічних кешованих ресурсів — **не менше 31 дня (2678400 с)**. Вона охоплює HTML обох мов, публічний Markdown, каталоги, статичні дані, discovery/SEO-файли, CSS, JavaScript, зображення, відео та шрифти. Короткий edge TTL не є способом підтримувати свіжість. Після змін потрібен точковий purge відповідних URL і їхніх залежностей.

Це вимога до CDN, не обіцянка фактичного зберігання кожного об’єкта протягом усього TTL: Cloudflare може витіснити його раніше. Наявність правила не є доказом HIT або свіжості.

## Edge та браузер — різні рівні

- Версійовані ресурси використовують content hash у `v`; повний query string залишається частиною cache key. Чинний місячний браузерний TTL не зменшувати. Річний browser immutable не вмикати без окремого доказу зберігання історичних ресурсів.
- Змінювані HTML, каталоги й discovery-файли отримують щонайменше місяць на edge, але браузер має перевіряти їхню актуальність на CDN. Purge Cloudflare не очищає кеш браузерів; встановлення місячного browser max-age для HTML зробило б purge неефективним для повторного відвідувача.
- Приватні відповіді, авторизовані запити, POST та інші операції зі зміною стану не є статичними ресурсами. Невідомі URL і помилки не можна зберігати на місяць як успішний контент.
- Власник окремо погодив місячний CDN-кеш публічного Markdown, залишивши MCP POST без кешу. Браузерний `no-store` для Markdown та публічних MCP-документів зберігається, але їхні перевірені копії зберігаються окремо у Workers Cache API на 2678400 с. Це не ввімкнення загального Workers Caching перед Worker: він лишається вимкненим. DNS, безпека, індексація, журнали й consent не змінюються.

## Публічні Markdown і MCP-документи

- `PUBLIC_EDGE_CACHE_ENABLED=true` вмикає лише Cache API для успішних публічних GET/HEAD документів. MCP POST, preflight, помилки, авторизовані запити й недопустимі Accept/query не використовують цей кеш.
- Ключ містить **шлях самого Markdown/JSON документа та повний SHA-256 його байтів**. URL HTML-сторінки не є ключем Markdown; мовні шляхи розділені. Невідомі запити не стають новими capability endpoints.
- Після фактичного cache hit байти, ETag і строк кешу перевіряються. Version, language, MIME, discovery та інші клієнтські заголовки формуються з поточного matching релізу, не зі старих метаданих кешу. Незмінний документ можна повторно використати; інший вміст отримує інший ключ.
- Недоступність Cache API не повинна підміняти чи ламати публічні факти: повертаються точні вбудовані байти, а `UNAVAILABLE`/`ERROR` лишаються невиконаним пунктом cache acceptance. `REPAIRED` не зараховується як коректний попередній HIT.
- `X-Piskor-Edge-Cache`, `X-Piskor-Edge-TTL`, `X-Piskor-Edge-Key` і `X-Piskor-Edge-Purge-Prefix` описують фактичну операцію й керовану копію. Cache API HIT не означає, що запит узагалі не виконував Worker. TTL не підтверджує гарантованого фізичного утримання об’єкта.
- Cloudflare не гарантує single-URL purge Worker-created custom keys. Використовувати **глобальний prefix purge** точного шляху документа без query, який очищає всі його хеш-версії. `cache.delete()` — лише локальний для одного датацентру і не замінює глобальну інвалідацію. Після purge підтвердити MISS та наступний HIT у контрольному запиті.

## Перед релізом

- Згенерувати інвентар фактичного Pages-артефакту: публічний URL, SHA-256, тип ресурсу, посилання на залежності. Перевірити, що версії медіа/шрифтів/CSS/JS відповідають фактичним байтам, включно з srcset, постерами, галереями, CSS URL та JS-посиланнями.
- Порівняти з попереднім **опублікованим** інвентарем, а не довільною локальною збіркою. У purge включити змінені й видалені стабільні URL та транзитивних споживачів. Нові URL не мають попереднього успішного кешу, але могли мати кешований404; додати їх до контрольованого purge.
- Для нового кейсу охопити мовну пару, загальні й річні каталоги, сторінки зі зміненими рекомендаціями, project-catalog.json, llms.txt, sitemap і змінені discovery-документи. Імена файлів чи перелік лише двох каталогів не замінюють графа залежностей та порівняння байтів.
- Якщо попереднього інвентарю немає або змінилася сама політика кешу, підготувати явний bootstrap-список усіх публічних змінюваних документів. Не використовувати Purge Everything. Список має бути придатний для точного URL purge пакетами до 30 адрес у чинному dashboard; Cache API копії мають окремий список префіксів.

Збірка запускає `scripts/cache_policy.py` й зберігає окремий CI artifact `cache-policy`, поза публічним сайтом. Для точного порівняння з попереднім опублікованим артефактом:

```sh
python3 scripts/cache_policy.py --site ACTUAL_MAIN_PAGES --revision FULL_MAIN_SHA --previous PREVIOUS_PUBLISHED_MANIFEST --out NEW_CACHE_REPORT_DIRECTORY
```

`manifest.json` містить байти/хеші й render-залежності, `purge-plan.json` — точні URL batches і Markdown prefixes. Звичайні навігаційні посилання не утворюють граф тотальної інвалідації всіх сторінок. Змінені байти документів, нові/видалені файли й транзитивні споживачі змінених ресурсів перевіряються окремо.

## Публікація та перевірка

- Cloudflare змінювати після мерджу погодженого PR, успішного matching main Pages deployment та перевірки bundle/manifest/байтів Worker. Підготовка PR або документації ще не змінює активну політику.
- Зберегти поточні rule IDs, expressions, порядок, TTL/status-code TTL, cache key та протокольні винятки. Міняти лише поля погодженого плану; не підміняти весь ruleset і не вмикати платний тариф або нові повноваження.
- Погоджений patch наявного правила зафіксований у `cloudflare/cache-policy.json`: GET/HEAD, edge TTL 2678400 с, browser bypass/revalidation і no-store для статусів від 300. `PURGE` доданий до method expression для сумісності з інвалідацією Cloudflare, не для кешування операцій зміни стану. Правило лише з GET може не збігатися під час single-file purge. Зберігати правило версійованої статики, origin Markdown bypass і вимкнений Workers front cache.
- Після paired Pages/Worker релізу виконати точковий purge підготовленого набору. Не очищати все статичне медіа через додавання одного кейсу. Ресурс за новим content-hash URL не потребує очищення незмінених версій.
- Після purge звірити HTTP status, MIME, повний SHA-256, canonical/hreflang, агентні факти та revision з реальним main artifact. Контрольований повторний запит має показати `MISS → HIT` і коректний Age. TTL перевіряти також у control plane: edge TTL не видно безпосередньо в browser Cache-Control.
- Виконати чергування HTML/Markdown, no-store/методні/404 перевірки, native WebMCP обома мовами, readiness, а потім PSI. Не оголошувати кешування виконаним, спираючись лише на збережений rule або один HIT.
- Перед відкатом також підготувати purge змінених URL. Повернення origin або правила не видаляє вже закешовані байти. Старі URL медіа/контролерів зберігати для попереднього HTML.

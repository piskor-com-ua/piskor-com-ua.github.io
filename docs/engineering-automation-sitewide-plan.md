# Наскрізний напрям інженерної автоматизації PISKOR

## Мета

Зробити автоматизацію помітною та зрозумілою послугою PISKOR на всьому сайті: від першого знайомства і сторінки послуги до портфоліо, підтверджених кейсів, контактів та агентських discovery-ресурсів. Пояснювати цінність через сценарії користування і координацію інженерії, а не через загальний список гаджетів.

## Фактичні межі

- На головній уже заявлено проєктування автоматизації освітлення й мультимедіа, клімату, безпеки, приводів, енергії та побутових сценаріїв. Сторінка послуги подає ці напрямки як те, що можна розглянути залежно від завдання й сумісного обладнання, а не як встановлений комплект для кожного клієнта.
- Кейс будинку у Брюховичах містить джерельно підтверджений опис інтегрованої автоматизації конкретного реалізованого об’єкта. Він є прикладом і доказом досвіду, не універсальною специфікацією.
- В інших кейсах статус автоматизації має братися тільки з опублікованого опису/фактів конкретного об’єкта. Відрізняти передбачене кресленнями, рекомендований сценарій, встановлене та перевірене.
- Не вказувати бренди, шини, протоколи, сумісність, монтаж, пусконалагодження, економію або гарантії, доки їх не підтверджено для відповідної послуги чи кейсу.

## План за етапами

### Перший реліз: маршрут послуги і базове discovery

- Створити парні сторінки UA/EN з унікальними заголовками, метаданими, мовними парами, описом підходу, напрямами систем, етапами співпраці, межами складу та посиланням на підтверджений кейс.
- Пов’язати сторінки з головною, карткою/діалогом послуги, каталогами, кейсами та 404. Зберігати описові тексти посилань.
- Додати `Service` і правильний `BreadcrumbList` лише до сторінок послуги. Зберігати Organization/Website graph і не додавати непідтверджені рейтинги чи відгуки.
- Додати дві мовні сторінки до `llms.txt` та agent skill guide; доступна HTML-сторінка лишається джерелом істини.
- Не додавати JavaScript або декоративні медіа для цього контентного маршруту. Використати системні стилі, статичну семантичну розмітку й адаптивний CSS.
- Обмежувати критичний CSS двома маршрутами послуги за фактичним DOM і перевіреними станами згоди/агентських контролерів; не завантажувати стилі кейсів портфоліо, які сторінка не використовує.
- Зберегти `noindex,nofollow`; не змінювати Cloudflare.

### Другий етап: підтверджена матриця послуг

- Узгодити для кожного напрямку, що саме PISKOR виконує власною командою, з партнерами або лише проєктує: аудит, концепція сценаріїв, креслення/специфікація, комплектація, монтаж, інтеграція, налаштування, супровід.
- За наявності доказів додати сторінці послуги чіткі межі відповідальності, сумісність з інженерними розділами, резервне ручне керування та процедуру приймання.
- Не розмножувати тонкі SEO-сторінки за протоколами/брендами. Створювати сторінку під окремий пошуковий намір лише за наявності унікальної експертної інформації, прикладів і пропозиції PISKOR.

### Третій етап: портфоліо і машинні факти

- Для кожного кейсу з потенціалом автоматизації переглянути вихідні креслення, специфікації та підтвердження реалізації. Додати окремі поля для категорій і статусів лише якщо вони відтворюють видимий текст і джерела.
- Генерувати людський каталог, Markdown, `llms.txt`, JSON та WebMCP/MCP відповіді з одного перевіреного набору фактів. Не підтримувати паралельні ручні списки.
- Розглянути read-only `get_service_details` для WebMCP і HTTP MCP лише після розширення спільного контракту, negative tests, discovery schema та Worker bundle. До цього агенти переходять на сторінку послуги й чинні інструменти пошуку кейсів/контактів.

### Четвертий етап: перевірка й масштабування

- Перевірити UA/EN маршрути, canonical/hreflang, structured data, внутрішні посилання, sitemap/Markdown генерацію та noindex.
- Перевірити з Chrome Agentic Browsing реєстрацію наявних інструментів, доступне дерево, клавіатурний доступ, layout stability та правдиве знаходження послуги/кейсів. Не додавати фіктивний WebMCP API або форму.
- Виміряти FCP/LCP/SI окремо для кожного нового URL в mobile і desktop. Спільні зміни на інших сторінках перевірити на регресію; не оголошувати весь сайт відповідним, спираючись лише на нові сторінки або одну вибірку.
- Публічну індексацію та будь-які зміни Cloudflare розглядати окремо після дозволу й окремого release gate.

## Приймання першого релізу

- Обидві сторінки послуги доступні через звичайні HTML-посилання з головної/каталогів/портфоліо та згенерованого `llms.txt`.
- Структуровані дані валідні, мовні альтернативи взаємні, контактні посилання працюють, клавіатурний фокус помітний.
- На мобільному та desktop немає горизонтального переповнення; сторінки мають семантичні заголовки й не потребують JS.
- Сценарії і статус реалізації не вигадують фактів; `noindex,nofollow` присутній.
- Production публікацію перевірити після мерджу; Cloudflare не змінювати в межах цього напряму.

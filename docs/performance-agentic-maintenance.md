# Підтримка швидкодії та Agentic Browsing

Ці вимоги обов’язкові для нових функцій, кейсів і змін спільних шаблонів. Вони доповнюють AGENTS.md та правила портфоліо. Не змінювати факти про проєкти заради пошуку, структурованих даних чи відповіді агента.

## Зображення й перший екран

- Картки каталогу використовують спільний клас portfolio-card-cover. Збірка генерує адаптивні WebP та AVIF 480/640/960/1440 px без збільшення оригіналу, справжні розміри й sizes зі спільної сітки. AVIF обирається нативним picture/source лише до 700 px; WebP зберігається для desktop, несумісних браузерів і попереднього HTML. Не створювати вручну окремі версії розмітки UA/EN.
- AVIF створюється з того самого вихідного кадру, що й WebP, з quality=60, speed=6 та max_threads=2; не перекодовувати вже зменшений WebP. Після зміни енкодера або якості порівнювати деталі матеріалів, світло, градієнти, кадрування, обсяг передачі й час декодування. CSS-breakpoint, media у source та sizes мають узгоджуватися. Не підміняти запасне зображення й не прибирати його src/srcset, alt, розміри чи eager/lazy/fetchpriority.
- Перша обкладинка загального або річного каталогу завантажується eager з fetchpriority high; наступні — lazy. LCP-зображення кейсу також не може бути lazy. Не призначати high всім карткам.
- Зберігати якісні оригінали. Обробляти тільки згенерований _site; не змінювати зміст кадру й не підміняти зону простору. Галерея використовує більший кадр за потреби.
- Справжні width/height та дескриптори srcset визначає збірка. Після зміни кадрування перевіряти композицію, чіткість, перший екран і CLS.
- Нові формати мають одночасно отримати підтримку оптимізатора, перевірок посилань та allowlist публічного артефакту.

## Стилі, шрифти та доступність

- Спільна сітка залишається в portfolio.css і case-story.css, з portfolio-columns та portfolio-gap. Згенерований catalog-bundle.css об’єднує спільні джерела в початковому порядку. Збірка вбудовує цей невеликий bundle в каталоги, з абсолютними URL медіа й шрифтів, щоб прибрати блокуючий запит. Inline-стилі й bundle не редагувати вручну; змінювати спільні джерела. Окремий bundle зберігається для попереднього HTML.
- Використовувати локальні WOFF2 та font-display swap. Preload має збігатися з реально використаним URL і накресленням. Під час заміни шрифтів зберігати українські гліфи, цифри, м² і стрілки; зберігати ліцензію.
- У каталогах preload обох реально використаних накреслень і спільні inline-стилі розташовані перед великим SEO/JSON-LD блоком. Не переносити їх після структурованих даних. Не вбудовувати шрифти в кожен HTML без парного вимірювання холодного й теплого переходу: це збільшує документ і втрачає повторне використання кешу шрифтів.
- Збірка створює піднабори шрифтів з усіх HTML/CSS/JS, включно з HTML entities, Unicode/CSS escapes і динамічними текстами банера, галереї та помилок. Додатково зберігає повну українську абетку й ASCII. Не генерувати піднабір лише з видимого першого екрана. Поточний бюджет двох WOFF2 — 40 000 байтів; збільшення потребує повторного вимірювання швидкодії. Оригінальні TTF і WOFF2 та ліцензія залишаються доступними для старого HTML/CSS.
- Контролер аналітики вбудовується без зміни логіки на початку body: він має бачити document.body і свій data-measurement-id до появи основного контенту. Не повертати залежність появи банера від зовнішнього JS-запиту. Зберігати відмову, згоду, відкликання, повторне відкриття та відсутність GA4 до згоди.
- Контраст звичайного тексту — щонайменше 4,5:1, великого — 3:1. Перевіряти також hover, focus, дрібні підписи й повідомлення.
- Зберігати клавіатурну навігацію, видимий фокус, семантичні назви, Escape та повернення фокуса після діалогу. Важливий контент і звичайні посилання доступні без виконання JavaScript.
- Зміни shared CSS перевіряти на всіх опублікованих проєктах обома мовами, на 390/768/1440 px. Знімки та автоматичні геометричні перевірки не замінюють оцінки змісту зображень.

## Ресурси та кеш

- Збірка додає content hash у query-параметр v для медіа, шрифтів і CSS/JS. CSS/JS хешуються після версіонування вкладених ресурсів. Не створювати посилання динамічним складанням частин імені файла.
- Зберігати шляхи ресурсів, які можуть використовуватися старим HTML. Видалення або перейменування потребує перевірки перехідного періоду, тривалості кешу та відкату. Старі TTF тимчасово зберігаються для попередніх HTML/CSS.
- Версії в URL забезпечують оновлення браузера. Вони не є сховищем історичних версій вмісту. Річний immutable не вмикати, доки немає гарантованого зберігання відповідних історичних ресурсів.
- Browser TTL і edge TTL перевіряти окремо; HIT Cloudflare не підтверджує довгий браузерний кеш.
- Cloudflare змінювати тільки після мерджу цього PR, успішного Pages deployment і живої перевірки версій ресурсів. Не застосовувати довгий TTL до HTML або project-catalog.json. Конкретний післямерджевий порядок наведено нижче.

## Дані та інструменти агентів

- Звичайні HTML-посилання, описові якорі та доступна галерея — основний інтерфейс. Не приховувати важливий зміст за агентним API.
- project-catalog.json і llms.txt генеруються з фінальних карток і сторінок. Не підтримувати паралельні вручну переписані описи чи окремі непідтверджені факти для агентів.
- Labels, статус, площа та рішення у відповіді інструмента мають відповідати видимому кейсу. Тільки прямі докази дозволяють назвати автоматизацію встановленою; пропозицію й потенціал передавати в їхньому опублікованому формулюванні.
- Поточні search_projects, get_project_details та get_contact_options читають публічні дані. Не додавати неявного надсилання повідомлень, заявок, згоди на аналітику чи інших побічних дій.
- Новий інструмент має одну зрозумілу функцію, схему входу, перевірку параметрів у коді, зрозумілі помилки, коректний результат без збігів і перевірку повторних викликів.
- Перевіряти чинну документацію WebMCP перед зміною інтеграції: API експериментальний. document.modelContext є поточною поверхнею; navigator.modelContext підтримує попередні trial-реалізації. Без API сайт працює звичайно й не завантажує агентний каталог.
- Наявність JavaScript-адаптера або unit-тестів не доводить реєстрацію інструментів у браузері відвідувача. Native WebMCP перевіряти окремо в сумісному браузері; потребу origin trial вирішувати окремо.
- llms.txt — допоміжний путівник; він не замінює robots, noindex чи згоду на використання даних і не гарантує появи в AI-пошуку. ARD-маніфест додавати лише для реального ресурсу після перевірки актуальної специфікації.

### Discovery та Origin Trial

- Збірка публікує `.well-known/ard.json` і сумісний `.well-known/ai-catalog.json` з одного джерела. На сторінках із WebMCP є відповідні `rel="ard"` і `rel="ai-catalog"`. Чинна ARD-пропозиція використовує перший шлях; Lighthouse 13.5.0 ще читає другий. Не підтримувати два незалежно відредаговані маніфести й не прибирати сумісність без перевірки нової версії Lighthouse.
- Запис описує реальний публічний ресурс `agent-skills/piskor-portfolio/SKILL.md`: пошук кейсів, читання підтверджених фактів, секцій і контактів, звичайна навігація без WebMCP. Його джерело — `agent-resources/piskor-portfolio/SKILL.md`. Список можливостей має відповідати фактично зареєстрованим інструментам. Не називати браузерний WebMCP адаптер віддаленим MCP-сервером і не вигадувати endpoint для викликів.
- `npm run test:discovery` після збірки перевіряє актуальну закріплену ARD-схему, conformance поточного Lighthouse, реальні цільові файли й JSON Schema інструментів. Схема, її upstream commit і ліцензія зберігаються в `scripts/schemas/`; вони не є публічним контентом. Після оновлення залежностей або пропозиції ARD повторити обидва валідатори.
- Для production Chrome потребує first-party WebMCP Origin Trial token. Офіційна реєстрація: https://developer.chrome.com/origintrials/#/register_trial/4163014905550602241. Станом на 18.10.2026 випробування активне для Chrome 149–162 до 30.03.2027; строк конкретного токена перевіряти окремо. Користувач надав first-party токен для `https://piskor.com.ua:443`, feature `WebMCP`, expiry `2027-03-30T00:00:00Z`, без third-party matching і субдоменів. Активацію та підпис перевіряти в Chrome на живому домені після deployment.
- Публічний токен записувати в `webmcp_origin_trial_token` у `_config.yml`; метатег з'являється перед `agent-tools.js` на тих самих сторінках. Порожнє значення не створює фіктивного метатега. Використовувати лише origin `https://piskor.com.ua`, без third-party matching чи всіх субдоменів. Не використовувати тестовий або чужий токен.
- Збірка перевіряє origin, feature, формат і строк токена; його криптографічний підпис та активацію підтверджує Chrome. Періодичний CI виявляє прострочення. До завершення строку поновити токен в тому самому процесі PR або прибрати його й залишити звичайну навігацію. Успішний тест із браузерним прапорцем не доводить активації production Origin Trial.
- Маніфести й skill не preload-ити і не запитувати при звичайному відкритті сторінки. JSON каталогу завантажується лише під час виклику відповідного інструмента. Після релізу перевірити HTTP 200 для обох well-known шляхів і skill, їхній вміст та короткий TTL/перевалідацію; не застосовувати місячний кеш до discovery-документів без версій.
- `WebMCP form coverage` залишається N/A, доки на сторінці немає справжньої форми. Пошук для людей є окремою UX-функцією: додавати його за потреби користування, з доступними підписами й declarative-анотаціями, а не для зміни показника аудиту. Не перетворювати згоду на аналітику або відкриття месенджера на автоматичне надсилання заявки.

## Валідація та докази

- Встановити requirements-build.txt, виконати python3 scripts/build-site.py, node --test scripts/test-agent-tools.js та git diff --check.
- Збірка перевіряє весь каталог і мовні пари, розміри та srcset, eager/lazy, хеші ресурсів, контраст, JSON-LD, SEO й noindex. Браузерну матрицю виконувати за scripts/check-portfolio-grid.js.
- Для продуктивності порівнювати щонайменше три прогони з однаковими Lighthouse, viewport, throttling, станом consent і холодним кешем. Зберігати медіану та розкид. Оцінки економії Lighthouse не підсумовувати.
- Для цілі mobile Speed Index ≤1 с виконувати щонайменше п’ять холодних прогонів із банером першого візиту, звітувати весь діапазон, а також FCP/LCP/CLS/TBT. Локальний сервер зі стисненням scripts/serve-benchmark.py потрібен для порівняння доставки тексту; результат без CDN/HTTPS не оголошувати production PSI. Окремо перевіряти теплий перехід і збережений вибір аналітики. Не приховувати банер, текст або зображення заради метрики.
- Перед парним бенчмарком перевірити, що кожен URL повертає байти саме своєї збірки: зайнятий порт може залишити старий сервер. Не запускати одночасно інший Lighthouse, збірку зображень або браузерну матрицю. Зберігати також викиди TBT і джерела довгих завдань, не вилучати невигідні прогони.
- Окремо перевіряти перший візит, відмову, згоду й відкликання аналітики та всі реально підключені трекери. Не додавати трекери й preconnect до них до згоди через оптимізацію швидкості.
- Агентний маршрут: знайти кейс, звірити опублікований статус, перейти до секції, перемкнути мову того самого кейсу, відкрити/закрити галерею та знайти контакти. Надсилання повідомлення не входить у цей маршрут.
- Локальна лабораторна оцінка не є production або CrUX-доказом. TBT не замінює INP. Agentic Browsing pass ratio не є оцінкою видимості в AI-пошуку.
- Зберігати noindex,nofollow до окремого явного дозволу. Підвищення SEO-балу не є дозволом на індексацію, PR — дозволом на merge, а успішний build — підтвердженням deployment.

## Після мерджу: Cloudflare

- Дочекатися Deploy Pages для merge commit. Перевірити UA/EN, CSS/JS, WOFF2, обкладинки, llms.txt, project-catalog.json і noindex на живому домені.
- Переконатися, що Cache Rules враховують повний query string, зокрема v. Не ігнорувати його в cache key.
- Browser TTL застосовувати лише до статичних медіа/шрифтів/CSS/JS з версіонованими URL. Користувач 16.10.2026 збільшив його до місяця (фактичний max-age=2678400); не повертати добу під час наступного релізу. Перевірити зміну v після нового вмісту та перехід зі старого HTML. Річний immutable потребує окремого обґрунтування зберігання історичних ресурсів.
- Зберігати короткий TTL/перевалідацію HTML, robots, sitemap, llms.txt та project-catalog.json. Не кешувати весь сайт правилом Cache Everything заради бала.
- Якщо ввімкнено короткий edge-кеш загальних каталогів, обмежувати його GET без query string для `/portfolio/` та `/en/portfolio/` на основному домені. Edge має використовувати Cache-Control origin і обходити кеш без цього заголовка; browser TTL — Respect origin TTL. Поточний origin max-age=600 не підміняти місяцем чи примусовими двома годинами. Після кожного Deploy Pages й перед перевіркою публікації виконати цільовий purge цих двох URL, перевірити новий HTML та повторний HIT з коротким Age. Не включати в це правило кейси, discovery, каталоги даних або невідомі URL; за проблем зі свіжістю вимкнути саме це правило.
- Перевірити реальні Cache-Control, CF-Cache-Status, холодний/теплий запит і післярелізний PageSpeed. За регресії повернути попередні Cache Rules.
- Збільшувати TTL далі лише після підтвердженого зберігання старих URL та перевіреного відкату. Підготовка коду не змінює поточних налаштувань Cloudflare.

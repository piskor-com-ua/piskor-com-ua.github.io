# Підтримка швидкодії та Agentic Browsing

Ці вимоги обов’язкові для нових функцій, кейсів і змін спільних шаблонів. Вони доповнюють AGENTS.md та правила портфоліо. Не змінювати факти про проєкти заради пошуку, структурованих даних чи відповіді агента.

За уточненням замовника від 18.10.2026 оптимізації мають зберігати початковий публічний дизайн commit `0870c3bf14e7e57e7f704a9d475f783a277de0cd`: композицію hero, шрифти, масштаби тексту, геометрію й кадрування фото, спільну сітку та взаємодії в обох мовах і режимах. Компактні фото 320×160 та заміна мобільного Roboto системним шрифтом із PR #53 не є дозволеним способом досягнення метрик. Оптимізувати доставку й виконання без нового вигляду; окремі зміни дизайну потребують явного погодження. Пороги нижче залишаються незмінними.

## Обов’язкові критерії для кожної сторінки

Оптимізації виконувати за окремим підтвердженням замовника для конкретного URL і мови, якщо замовник явно не погодив перелік сторінок одним завданням. Для погодженого переліку можна застосовувати спільні механізми на всіх названих URL; це не дозволяє вмикати їх на інших сторінках без окремого підтвердження. Аналіз, реалізація та публікація мають відповідати обсягу відповіді замовника; перевірка відсутності регресій лишається частиною поточного релізу.

Вимога замовника від 18.10.2026 діє для **кожної публічної HTML-сторінки обома мовами, у mobile та desktop**. Вона включає головні сторінки, усі сторінки меню, загальні й річні каталоги, кожен кейс і службові сторінки, зокрема 404.

| Показник | Обов’язковий поріг |
|---|---|
| First Contentful Paint (FCP) | **<1000 мс** |
| Largest Contentful Paint (LCP) | **<1000 мс** |
| Speed Index (SI) | **<1000 мс** |
| Agentic Browsing | **Усі застосовні аудити успішні; поточний контракт — 5/5**, із перевіркою реальних агентних сценаріїв |

Усі три часові пороги строгі: рівно 1000 мс є перевищенням. Для конкретного завдання замовник може задати тимчасову проміжну межу для названого переліку; вона не змінює загальний контракт для інших сторінок. Для мобільної серії з історичних 39 URL (`scripts/mobile-si-target-routes.json`) і окремого п’ятисторінкового follow-up (`scripts/mobile-si-followup-routes.json`) погоджена проміжна межа: FCP <1000 мс, LCP і SI <1500 мс; прагнути LCP і SI <1000 мс.

### Актуальний PSI follow-up із SI понад 1,5 с

Це production mobile baseline від 20.10.2026 до змін цього циклу; точні звіти та умови заміру збережені у follow-up manifest. Усі п’ять сторінок мають FCP <1 с, але SI перевищує навіть проміжну межу. Тому пріоритет — не погіршувати швидко завантажуваний LCP: лишити eager обкладинку/першу картку, а в погодженій когорті відкласти тільки нижню галерею й наступні картки. Для кейсів додатково застосовується перевірене звуження CSS до класів конкретного URL; невідомі або змінені скрипти, як і раніше, автоматично повертають повний stylesheet.

Окремий актуальний топ‑10 за мобільним Speed Index на production знято 20.10.2026 від `dc11e6a`; початкові URL, звіти PSI, FCP/LCP/SI, пристрій і throttling збережені в [`scripts/mobile-si-top10-routes.json`](../scripts/mobile-si-top10-routes.json). Для нового циклу перевіряти повністю вкладки **Insights** і **Diagnostics** на кожному звіті, а не лише scored opportunities: знімати forced reflow, dependency tree, DOM size, LCP breakdown/discovery, image delivery, CSS/JS bytes, main-thread work і long tasks. У повторному зрізі обкладинки залишалися eager, мали `fetchpriority=high` і були знайдені в початковому HTML; image-delivery opportunities, невикористаний CSS/JS, minification та render-blocking не мали оцінених заощаджень. DOM містив приблизно 205–489 елементів і не був позначений проблемою. PSI показав ланцюжок документа до Roboto Regular на всіх десяти URL, хоча стороннього origin для preconnect не запропонував; тому додати ранній preload саме цього локального шрифту в спільні шаблони, не змінюючи Roboto, ваги чи стилі. Forced reflow 33–86 мс з’являвся на семи звітах як `[unattributed]`; у коді перевірених контролерів немає підтвердженого синхронного геометричного читання, тому не приписувати знахідку `home-bootstrap.js` без trace-доказу. Перенесення consent-ініціалізації після розмітки сторінки зменшує роботу перед початком парсингу видимого контенту; зараховувати reflow усуненим лише якщо наступний PSI перестане його показувати. У LCP breakdown на проблемних URL головною складовою був element-render delay, тоді як discovery, eager/priority та розмір обкладинки вже були налаштовані; не переробляти обкладинку або її розмір без нового вимірюваного доказу. `is-crawlable` лишається навмисно негативним через `noindex,nofollow` і не змінюється без окремого дозволу на індексацію. Після релізу повторно перевірити ті самі 10 URL та всі згадані insights/diagnostics; не оголошувати інформаційну знахідку усунутою, якщо PSI досі її показує.

Перед реалізацією кожної серії зберігати PSI opportunities та diagnostics для кожного URL і пріоритезувати критичні рекомендації за очікуваним впливом на LCP/SI, оціненими байтами/часом і кількістю сторінок. Вважати рекомендацію усунутою лише після повторного аудиту, що більше не знаходить заощадження; інформаційну або неакційну знахідку закривати тільки з доказом, чому вона не застосовна. Для `Improve image delivery` фіксувати маршрут, DOM-вузол/селектор, вибраний `currentSrc`, фактичні розміри й байти; після змін шляхів або шаблонів повторно зіставляти знахідку саме з цією роллю зображення у зібраному сайті. Перевіряти всі знайдені вузли на кожному погодженому маршруті й повторювати Lighthouse/PSI до зникнення заощаджень або до доказового висновку про непридатність рекомендації. Не змінювати `sizes` чи дескриптори `srcset`, щоб браузер вибрав штучно малий файл; не знижувати роздільність нижче фактичної потреби DPR і перевіряти чіткість після зміни стиснення. Не приховувати зміст і не псувати Agentic/доступність для штучного проходження аудиту. Локальні Lighthouse-заміри допомагають діагностиці, але не підтверджують production PSI.

Повна підтримка Agentic Browsing охоплює семантичну й клавіатурну навігацію, доступні назви та стани елементів, правильні мовні й секційні посилання, узгоджені discovery-ресурси й актуальні дані, реєстрацію та виконання всіх реальних WebMCP-інструментів у сумісному браузері. Поза підтримуваним API зберігати звичайну доступну навігацію. Після оновлення Lighthouse перевіряти весь актуальний набір застосовних аудитів, не обмежуватися старим числом 5/5. Коректне N/A не є помилкою чи успішно перевіреною функцією; не створювати фіктивних форм, API або маніфестів заради оцінки.

Це критерії приймання, а не твердження про вже досягнутий результат. Якщо хоча б одна сторінка перевищує поріг або не має потрібного підтвердження, відповідний пункт залишається відкритим; не оголошувати весь сайт таким, що виконав вимогу.

## Agentic Browsing: пріоритет і зовнішня перевірка

- На вимогу замовника від 18.10.2026 спочатку перевіряти й виправляти Agentic Browsing, потім переходити до порогових Google PSI вимірювань. Використовувати [isitagentready.com](https://isitagentready.com/) додатково до Lighthouse і виконання реальних WebMCP-сценаріїв. Зберігати час, URL, увімкнені перевірки, повний результат і докази; оцінку профілю Content Site не видавати за результат All Checks.
- Оцінювати застосовність кожної рекомендації до реального сайту. Публічне портфоліо має анонімний read-only `GET /project-catalog.json` і окремий публічний HTTP MCP `/mcp` за [контрактом](public-http-mcp.md). OAuth-акаунтів, A2A-агента, платежів чи реєстрації агентів немає. Не вигадувати такі сервіси або endpoints заради оцінки. Каталог описує точний OpenAPI-контракт, а MCP — реальний транспорт і tools/list; браузерні WebMCP-інструменти залишаються окремим інтерфейсом.
- Головні сторінки мають доставляти змістовний HTML обома мовами до JavaScript. Генерувати його з того самого шаблону й текстів, що використовує клієнт; під час першого підключення JS зберігати DOM і вже вибрані зображення. Перевіряти навігацію й мовні посилання також без JS.
- Markdown-представлення генерувати лише з публічного фінального HTML, зі збереженням мови, змісту, контактів, посилань і `noindex`. Не публікувати приватні джерела. Додатково охоплювати англійський стан 404. Зміна HTML повинна оновлювати відповідний Markdown у тій самій збірці.
- Agent Skills discovery 0.2.0 і Poppy 0.1 є проєктами специфікацій. Індекс skill містить метадані й SHA-256 фактичних опублікованих байтів; оновлювати digest разом зі skill. Poppy `web: {}` оголошує тільки звичайне публічне читання сайту, без OAuth-сесій або агента студії. Зберігати чинні ARD URL для сумісності.
- Політика власника: **`ai-input=yes, ai-train=no, search=yes`**. Це окрема декларація Content Signals, не дозвіл зняти HTML `noindex,nofollow` або змінювати згоду на аналітику. Змінювати цю політику лише за вказівкою власника.
- Cloudflare-доставку Markdown, discovery-заголовків і DNS готувати в одному PR за [планом](cloudflare-agent-delivery.md), застосовувати після мерджу, успішного Pages та перевірки версії. Зберігати HTML як типовий формат, перевіряти MIME/HEAD/404 і відсутність змішування форматів у кеші. Обмежену content negotiation описувати точно, не називати її повною реалізацією HTTP Accept.
- Якщо isitagentready і звичайний HTTP-клієнт отримують різні формати, спочатку ізолювати Markdown-перевірку та застосувати [обмежену діагностику доставки](cloudflare-markdown-fallback.md). Не видавати заявлені сканером request headers за захоплені мережеві дані. Не підміняти MIME HTML, не додавати UA/IP-виняток або вигадані endpoints заради бала. Діагностику прибрати до підсумкового сканування й PSI. Після зміни доставки повторити перевірку всіх HTML/Markdown пар та негативних Accept/query/404 випадків.
- Для обраної замовником 19.10.2026 власної реалізації виконувати [план Markdown Worker](cloudflare-markdown-worker.md). Його bundle генерується з фінального Pages artifact й оновлюється після **кожної** публікації відповідного контенту; старий embedding не може залишатися джерелом фактів. Cloudflare застосовується після мерджу та перевіреного Pages, з quota fail-open, вимкненими logs/preview і перевіркою версії/байтів. Наявність bundle у CI не є доказом його активації чи scanner PASS.
- На `/` і `/en/` Worker може повертати Markdown для query, які не містять декодованого параметра `lang`. Без `lang` на `/` fallback завжди український, незалежно від `Accept-Language`; явний шлях `/en/` зберігає англійську версію. HTML лишається типовим форматом; `lang` зберігає чинний мовний перехід. Новий функціональний query-параметр головної потребує одночасного перегляду Worker-контракту й GET/HEAD перевірок. Не переносити це послаблення на каталоги, кейси, 404 або прямі Markdown URL без окремного обґрунтування.
- Для повного PSI-покриття використовувати `scripts/collect_pagespeed.py`: інвентар артефакту, окремі режими й повтори, імпорт публічних звітів та матрицю приймання. Кеш попередньої версії є діагностикою; він не замінює свіжі післярелізні вимірювання. Квоту API, runtime/HTTP-помилки, редиректи й відсутні звіти фіксувати явно.
- Розбирати кожен Performance-інсайт по конкретному URL, елементу та заявленій економії мілісекунд/байтів; спершу виправляти найбільший вимірюваний внесок у FCP/LCP/SI. Закривати рекомендацію лише після свіжого звіту з нульовою економією або задокументованої відсутності дії. Інсайти без вимірюваної економії не виправдовують ризикових змін: у поточному PSI cohort forced reflow мав 0 ms savings, а dependency-tree не визначив жодного придатного preconnect-origin. Локальний Lighthouse підтверджує діагностику кандидата, але не production PSI.
- API-збір виконується послідовними раундами: кожен обраний URL і mobile/desktop отримують один відсутній повтор перед наступним раундом. Це розносить повторні запити того самого ключа без паралельності, cache-busting або додаткових запитів; свіжості відповіді не гарантує, особливо для малої вибірки URL. Кешовані завершені слоти, включно з невдалими за швидкістю, не вимірювати повторно заради проходження. Повторний однаковий `fetchTime` для того самого URL і режиму зупиняє збір як дублікат; ліміт запитів і зупинка на квоті зберігаються, наступний явний запуск заповнює лише відсутні слоти.
- [Офіційний PSI v5 Discovery](https://pagespeedonline.googleapis.com/$discovery/rest?version=v5), revision `20261013`, перевірений 18.10.2026, містить `AGENTIC_BROWSING`. Колектор запитує точні enum `PERFORMANCE`, `ACCESSIBILITY`, `BEST_PRACTICES`, `SEO`, `AGENTIC_BROWSING`, без застарілої `PWA`. Це перевірка допустимості параметрів за первинними метаданими, а не доказ успішного API-запуску. Фактична відповідь повинна містити застосовні Agentic-аудити: старі або часткові звіти без них не проходять приймання.
- Дві історичні адреси `2026/bedroom-lighting-automation` обома мовами отримують повний підготовлений HTML справжнього кейсу `2021/two-level-loft-lviv` через явну map у `scripts/compatibility_pages.py`. Це прямі compatibility entries, не новий кейс 2026 року: canonical, hreflang, факти, каталог і JSON-LD залишаються 2021. Не додавати мережевого переходу або pathname rewrite; старі fragment IDs відновлює спільний контролер. Кожна адреса має власне Markdown-представлення й власну PSI-серію; швидкість canonical не успадковується як доказ. Перевіряти один document request, контент без JS, галерею, контакти та мовний перехід.
- Колектор також вміє зберігати справжні оголошені redirect aliases: meta refresh має збігатися з canonical на тому самому origin і вести до наявної сторінки контенту з тією самою явно вказаною мовою `uk` або `en`, а не іншого alias. Правильний кінцевий URL не зупиняє збір решти сторінок, але його сирі метрики не підтверджують час входу через alias. Статус `expected-routing-entry-timing-unverified` лишається неперевіреним і блокує `all_pages_pass`; неочікувані переходи й прострочені докази — помилки. Не перетворювати такі рядки на N/A або автоматичний canonical pass.

## Зображення й перший екран

- Картки каталогу використовують спільний клас portfolio-card-cover. Збірка генерує адаптивні WebP 480/640/960/1440 px і відповідні AVIF без збільшення оригіналу. Проміжні кандидати можна додавати за реальною потребою DPR, зберігаючи початкові розміри й кадрування CSS. Розміри й sizes мають відповідати справжній геометрії фото. AVIF обирається нативним picture/source лише до 700 px; WebP зберігається для desktop, несумісних браузерів і попереднього HTML. Не створювати вручну окремі версії розмітки UA/EN.
- AVIF створюється з найбільшого наявного вихідного кадру, з speed=6 та max_threads=2; не перекодовувати вже зменшений WebP. Початковий профіль quality=60 є базою порівняння; інша якість потребує перевірки на початковому розмірі відображення й DPR, а не на штучно зменшеній рамці. Початкові WebP та повні галерейні файли не змінюються. Після зміни енкодера або якості порівнювати деталі матеріалів, світло, градієнти, кадрування, обсяг передачі й час декодування. CSS-breakpoint, media у source та sizes мають узгоджуватися. Не підміняти запасне зображення й не прибирати його src/srcset, alt, розміри чи eager/lazy/fetchpriority.
- Перша обкладинка загального або річного каталогу завантажується eager з fetchpriority high; наступні — lazy. LCP-зображення кейсу також не може бути lazy. Не призначати high всім карткам.
- Адаптивний preload першої мобільної обкладинки генерується з фактично першої картки після сортування/фільтра року. Його type, media, imagesrcset та imagesizes мають точно збігатися з picture/source, включно з версіями URL. Розміщувати після viewport перед шрифтами та SEO, не задавати один фіксований розмір, не preload-ити одночасно AVIF і WebP. У браузері перевіряти один запит до обраного currentSrc на різних DPR і відсутність мобільного preload на desktop.
- Зберігати якісні оригінали. Обробляти тільки згенерований _site; не змінювати зміст кадру й не підміняти зону простору. Галерея використовує більший кадр за потреби.
- Справжні width/height та дескриптори srcset визначає збірка. Після зміни кадрування перевіряти композицію, чіткість, перший екран і CLS.
- Для погодженої мобільної серії зі Speed Index понад 1 с дозволене відкладання лише позаекранних галерейних і наступних карткових зображень: зафіксований список URL має бути джерелом точного охоплення. Завантажувати при наближенні до viewport (поточний root margin — 250 px), а також за фокусом/активацією; зберігати розміри, alt, повний контент для агентів, початкову галерею після відкриття й `<noscript>`-запасний варіант із повними src/srcset. Не відкладати обкладинку кейсу або першу картку каталогу; при відсутності IntersectionObserver активувати всі зображення. Перевіряти scroll, клавіатурний доступ, галерею, no-JS і мережеві запити в реальному Chromium. Legacy redirect aliases спершу мають бути матеріалізовані як підготовлені canonical-копії, після чого до них застосовуються ті самі route-scoped правила. Валідація порівнює агентний і видимий зміст точно, дозволяючи лише перевірені delivery-відмінності.

Це адресні зміни доставки/виконання без переміщення блоків або зміни дизайну; результат підтверджувати новими однаковими production PSI звітами та браузерною перевіркою.
- Для свіжих поточних SI-зрізів розширювати CSS pruning і HTML minification лише на виміряні canonical case URL, які ще не належать історичній 39-route когорті. - У цій самій серії для десяти маршрутів із початковим LCP не нижче 1,5 с додається мобільний AVIF-кандидат 832 px у responsive srcset та відповідному preload. Генерувати кандидати лише з найбільшого доступного вихідного кадру, не змінювати вихідні WebP, повні галереї, кадрування, рамки й desktop-ресурси. Перевіряти збіг URL/версії preload і source, фактично обраний currentSrc, чіткість деталей у природному CSS-розмірі та DPR; не поширювати якість на інші маршрути без доказів.

Окремий профіль q40 дозволений лише для цих трьох URL: зберігати фактичні 640×480 пікселів для обкладинок «Забави» та 640×360 для широкої обкладинки Vasha Terasa; для кожної перевіряти DPR/srcset, розмір, природну різкість і Image Delivery після зміни. - У базовій мобільній серії 19.10.2026 Image Delivery мав 19 елементів на 11 з 39 маршрутів: 16 lazy-зображень і три eager LCP-картки. Позаекранні джерела відкладаються лише в цій виміряній когорті; три перші картки оптимізуються окремими перевіреними AVIF-профілями. Для поточного плоского логотипа повнорозмірний WebP менший за зменшені Lanczos-версії; не додавати варіанти без порівняння байтів, прозорості та чіткості.
- Нові формати мають одночасно отримати підтримку оптимізатора, перевірок посилань та allowlist публічного артефакту.
- Для кейсів `sizes` має враховувати справжню геометрію `object-fit: cover`, а не лише ширину CSS-контейнера. Зміна висоти, пропорції або селектора може змінити потрібну роздільність. Перевіряти всі кейси на 390, 700, 701, 1440 і 1956 px через `scripts/check-case-density.cjs`; це перевірка геометрії, яка доповнює візуальний перегляд і не є доказом швидкодії.
- На desktop картки каталогу мають рамку 1.42:1 та `object-fit: cover`. Для native ratio `r` потрібна ширина джерела дорівнює ширині рамки × `max(1,r/1.42)`; широке фото потребує більшого кандидата через обрізання. Генератор перевіряє цю геометрію CSS, а браузерна перевірка щільності охоплює всі загальні й річні каталоги разом із кейсами.
- На мобільних зберігати початкові рамки каталогу й обкладинок кейсів та їхній `object-fit: cover`; не замінювати їх на 320×160 або `contain`. Базова обкладинка зберігає `height:min(72vw,730px)` і `object-position:center 58%` разом із наявними уточненнями конкретних кейсів у `case-story.css`; каталог — рамку 1.42:1. `sizes` враховує справжню ширину джерела після cover-кропу на кожному breakpoint, включно з широкими фото. Зберігати початкову поведінку hover і доступ до повного кадру в галереї.
- Різні рецепти обкладинок і галерей мають незалежні вихідні шляхи й ключі кешу. Перша картка каталогу використовує той самий mobile source і preload; інші картки залишаються lazy. Native DPR визначає справді потрібного кандидата, не примушувати менший файл через неправдивий `sizes`. Дедуплікація надає попереднім URL пріоритет перед новими профілями, якщо байти однакові. Старі AVIF каталогу зберігати також тоді, коли новий HTML уже не посилається на них або переписує однакові файли: місячний кеш HTML може містити попередній srcset. Не підвищувати unreferenced файли до нового canonical URL дедуплікації; звіряти попередні опубліковані шляхи й SHA-256, а не лише нові посилання.
- На мобільній головній зберігати початковий hero з фоновим фото на всю рамку, накладеним текстом, початковими відступами й типографікою. Не переносити фото під текст заради LCP або SI. Окреме кадрування ресурсу дозволене лише з доказом, що воно прибирає виключно невидимі за початковим CSS пікселі та відтворює ті самі видимі координати й щільність на всіх відповідних viewport. Preload і source повинні мати однакові media, candidates і sizes; desktop зберігає повне початкове фото. Перевіряти фактичний currentSrc, композицію й положення consent у UA/EN.
- Медіа інтерактивної історії завантажуються при наближенні до секції, без довільної часової затримки. Перевіряти перший візит, прямі `#story`/`#contact` переходи, reduced motion, зміну мови й останній запитаний кадр; без JS зберігати статичний перший кадр. Не підміняти відкладене завантаження приховуванням доступного змісту.

Не переносити це правило на обкладинку або інше LCP-відео. За [документацією web.dev](https://web.dev/articles/lazy-loading-video), підтримувані браузери відкладають також poster; браузери без підтримки ігнорують атрибут і зберігають звичайне відтворення.

З JS до наближення не було запитів poster/MP4; без JS poster також відкладався, але metadata запитувалася одразу. Це коректний нативний fallback, а не збій. Після оновлення браузерів повторювати мережеву перевірку, прокручування й відтворення; ці локальні докази не замінюють PSI приймання.

Зберігати явні `src` у template для версіонування, шрифтів і аналізу динамічних CSS-станів. Перевіряти перший клік меню, обидва мовні переходи, клавіатуру, hash, відмову мережі та повторну спробу; контролери не повинні виконуватися двічі. Статичний зміст, native-навігація й глобальні агентні інструменти доступні незалежно від історії.
- На головних `/` та `/en/` збірка після версіонування вбудовує незмінені спільні `agent-tools.js`, `home-bootstrap.js` і `url-compat.js` у початковому порядку. Inline-код розташований наприкінці body й виконується на `DOMContentLoaded`, коли контактний DOM уже доступний, до `load`; реєстрація WebMCP не залежить від скролу чи першого кліку. На відомих кейсах той самий перевірений механізм вбудовує `agent-tools.js` і `portfolio.js`; на загальних/річних каталогах та 404 — тільки `agent-tools.js`. Профіль визначають разом шлях документа й класи body; редиректи та невідомі сторінки зберігають зовнішні контролери, а підготовлені compatibility copies — повний контракт свого canonical-документа. Усі плани перевіряються до запису будь-якої сторінки. Для кейсів, каталогів і 404 дозволений лише явно перевірений набір зовнішніх скриптів із точними атрибутами, версіонованим hash і порядком: крім вбудовуваних контролерів, необов’язковий `url-compat.js` після контролерів кейсу або обов’язковий `not-found.js` перед агентним контролером 404. Нові зовнішні залежності потребують перегляду порядку виконання й зупиняють збірку. Початкові зовнішні контролери мають бути прямими активними дочірніми елементами head, а вбудовані — body; не активувати код із template, noscript або inert-контейнера. `not-found.js` і legacy `url-compat.js` залишаються зовнішніми defer: мова 404 визначається до реєстрації інструментів, а load/hash навігація працює після DOM-ready налаштування галереї. Зберігати Origin Trial у head перед контролером і всі зовнішні JS-файли для попереднього кешованого HTML. Перевіряти також теплі переходи: повторення коду в HTML може збільшити їхній трафік; локальний холодний виграш не є доказом швидкості всіх URL або production. Збірка перевіряє повний SHA-256, точний код, обгортку, порядок і одноразове виконання; зміни `async`, `type`, `nonce`, `integrity`, залежність від `currentScript` або власний `DOMContentLoaded` потребують перегляду цього механізму. Не правити згенерований inline-код вручну.
- Кеш AVIF у `output/image-cache` є відтворюваним прискоренням збірки. Ключ має включати вихідні байти, версію енкодера та повний рецепт, зокрема quality і crop; пошкоджений або невідповідний результат перекодовувати. Різні рецепти повинні незалежно повторно використовувати свої байти без перезапису іншого профілю. Не публікувати кеш і не вважати його браузерним/CDN-кешем.

## Стилі, шрифти та доступність

- Зберігати початковий Roboto на mobile й desktop, ваги 300/400, розміри, міжрядкові інтервали та ієрархію тексту. Системний стек залишається fallback, а не заміною дизайну заради метрик. Не обмежувати наявність `@font-face` або потрібний preload лише desktop, якщо Roboto використовується на мобільному. Перевіряти фактичні запити, застосований шрифт і українські гліфи на головних, каталогах, кейсах та обох 404-станах; нуль мобільних webfont-запитів сам по собі не є критерієм успіху. Спільна змінна/успадкування може впорядкувати CSS без зміни видимого результату.
- CSS інтерактивної автоматизації головної має явний `data-home-deferred-style="automation"` у controller template та noscript fallback. Збірка зберігає обидва link, версіонує URL і не перетворює їх на інертний inline style. Bootstrap повинен дочекатися CSS до виконання контролерів; помилка завантаження має допускати повторну спробу без подвійного виконання JS.

- Спільна сітка залишається в portfolio.css і case-story.css, з portfolio-columns та portfolio-gap. Згенерований catalog-bundle.css об’єднує спільні джерела в початковому порядку. Збірка вбудовує цей невеликий bundle в каталоги, з абсолютними URL медіа й шрифтів, щоб прибрати блокуючий запит. Inline-стилі й bundle не редагувати вручну; змінювати спільні джерела. Окремий bundle зберігається для попереднього HTML.
- Каталоги отримують консервативний піднабір inline CSS зі спільного bundle: збірка аналізує класи всіх мовних і річних каталогів та підключені контролери. Зберігати порядок декларацій, media queries, змінні, font-face, hover/focus, псевдоелементи й усі динамічні стани згоди. Динамічні класи контролерів записувати цілими літералами; не складати з фрагментів без оновлення аналізатора та перевірок. Невідомі/зовнішні контролери, escape-послідовності класів або помилка CSS повертають повний bundle. Окремий catalog-bundle.css залишається повним для старого HTML.
- Решта сторінок вбудовує стилі на початкових місцях каскаду: обидві головні разом, усі кейси разом, 404 окремо; невідомі сторінки використовують спільний консервативний набір. Зберігати також стани з підключених скриптів. Аналізатор підтримує чинні literal-префікси `device-`/`system-` у `classList.toggle`; довільний вираз мутації класу повертає повний CSS. Перевіряти реальний biodynamic-стан та інші інтерактивні режими, а не лише початковий екран.
- Окремий профіль дозволений лише для `/en/portfolio/2022/zabava-restaurant-sambir/`: `scripts/zabava_first_paint.py` працює з фінальним generated artifact після CSS pruning. Він відтворює Roboto 300–400 із поточних статичних masters без IUP-округлення й перевіряє точні контури, advance, hmtx і вертикальні метрики. Inline-піднабір охоплює весь опублікований англійський текст, consent, CSS content і динамічні підписи; complementary unicode-range поточних глобальних 300/400 зберігає повну UA/ASCII-доступність. Оригінальні шрифти й ліцензія залишаються. Ваги 500/700 додатково порівнювати в браузері; самі endpoint-тести не доводять однаковий синтез жирності.
- Variable payload оголошується двома `@font-face` з фіксованими CSS-вагами 300 і 400 та тим самим data URI. Не замінювати їх одним range `300 400`: перевірка Chrome виявила, що в такій комбінації complementary faces не завантажуються для UA/додаткових ASCII. Розділення unicode-range зберігає гліфи, але не гарантує кернінг між довільними символами з різних файлів. Поточний опублікований EN-текст повністю входить у critical subset; новий текст, consent, CSS-generated content або довільний editable input потребують повторної перевірки фактичного shaping, а не лише cmap/наявності гліфів. Не приховувати втрату міжшрифтового кернінгу штучного stress-тексту як повну типографічну еквівалентність.
- Той самий профіль вбудовує точні WebP-байти обох логотипів і додатковий повнокадровий AVIF `704w` у чинний mobile srcset та його preload. Не підміняти `sizes`, DPR або ширинні дескриптори: інші екрани мають обирати чинні зовнішні варіанти. Обкладинка q28/speed0 сильніше згладжує дрібні текстури рослин, дерева й оббивки порівняно з попереднім q35; композиція, кадрування, кольори та геометрія зберігаються. Це явний компроміс стиснення, не lossless і не незмінена якість. Повнорозмірна галерея та всі зовнішні кандидати зберігаються. Перевіряти вигляд у фактичному CSS-розмірі та повний кадр, а не лише кількість байтів. Зміна енкодера або quality потребує нового візуального порівняння й холодних вимірювань; тонкий локальний запас не є production-прийманням.
- Для цього URL CSS inventory додатково обмежений його HTML і точно перевіреними ревізіями контролерів. Невідомий або змінений controller/hash/wrapper повертає повний CSS. Логічні селектори можна прибирати лише за доведено відсутнім обов’язковим зовнішнім класом; невідомі функції, помилки й nesting зберігаються. Оновлення hash allowlist потребує повторної перевірки всіх динамічних станів.
- `html-minifier-terser` закріплений у lockfile; `npm ci --ignore-scripts` потрібен до Python-збірки. Компіляція дозволена лише явному EN URL, після перевірки сирих source hashes і CSS pruning. Після неї контролери перевіряються як точний результат того самого pinned transform, зі збереженням source hash, порядку й once/DOMContentLoaded-контракту. Довільний digest або схожий код не замінює цю перевірку. Решта URL зберігає попередні байти.
- Субсекундні локальні H2/Brotli-вимірювання цього профілю не доводять production PSI. Окремо перевіряти холодний браузер, теплий перехід, усі потрібні DPR, звичайний і no-JS перегляд, галерею/відео/consent, native WebMCP та післярелізний PSI. Усі мережеві представлення й винятки доставки описані в [контракті Worker](cloudflare-markdown-worker.md). Не переносити профіль на наступну сторінку без підтвердження замовника.
- Лише на погодженому EN Zabava `zabava-agent-tools.cjs` генерує початкову реєстрацію трьох WebMCP tools і окремий модуль виконання з того самого перевіреного `agent-tools.js`. Схеми, описи, read-only annotations, валідація аргументів і результати не підтримуються другою ручною копією. Реєстрація залишається на DOM-ready; модуль завантажується лише при виклику інструмента, успішний import і каталог використовуються повторно. Помилка import допускає обмежену повторну спробу з новим URL; перевіряти реальне виконання, зокрема після першої мережевої помилки. Зберігати точний source SHA, детермінований module hash і перевірку канонічного inline-коду. Під час наступної зміни реалізації зберігати попередні hash-named модулі доступними для вже кешованого HTML протягом строку його можливого використання.
- Шість позаекранних фотографій EN Zabava завантажуються через `IntersectionObserver` із запасом 750px, а також за фокусом або кліком. Геометрія, alt, sizes і responsive candidates зберігаються; спочатку відновлюються source/srcset, потім img/src. Без підтримки observer фотографії відновлюються одразу. Без JavaScript показуються оригінальні responsive pictures із noscript, а placeholder приховується тільки в цьому режимі. Не відкладати обкладинку, зміст, підписи чи посилання. Перевіряти швидке прокручування, прямий якір, клавіатуру, галерею, no-JS і незмінний Markdown. Перевірка щільності має спершу активувати фотографію справжнім прокручуванням: декодований SVG-placeholder не є доказом якості чи правильного srcset.

- `content-visibility:auto` застосовується тільки до посилання `.portfolio-card`, а не до його обгортки article. Доступна назва задається `aria-label` із повного видимого підпису картки: мітка, заголовок, опис і дія з тих самих Liquid-значень. Вона має включати видимий текст і залишатися доступною до прокручування; `aria-labelledby` на ще не відрендерений дочірній заголовок у Chromium може дати порожнє ім’я. Між сусідніми текстовими блоками картки зберігати справжні пробільні текстові вузли: Axe з’єднує текст без автоматичних пробілів на межах тегів. Статична перевірка не повинна додавати відсутні пробіли сама. Перевіряти всі іменовані посилання в нативному AX tree, також без JS, і фактичний `label-content-name-mismatch` після перевірок початкового AX/фокуса, навіть якщо аудит не впливає на бал. Оптимізація діє тільки для карток каталогу в `@media screen`, з оцінкою початкової висоти й запам’ятовуванням фактичної через `contain-intrinsic-block-size:auto`. Це не пагінація й не приховування: повний зміст залишається в HTML, а всі посилання з назвами — у нативному дереві доступності. Зберігати запас навколо картки для видимого фокуса; перевіряти всі річні якорі, перехід клавіатурою до далекої картки, прокручування вниз/назад і друк. Не застосовувати `content-visibility:hidden` до змісту.
- Використовувати локальні WOFF2 та font-display swap. Preload має збігатися з реально використаним URL і накресленням. Під час заміни шрифтів зберігати українські гліфи, цифри, м² і стрілки; зберігати ліцензію.
- У каталогах preload обох реально використаних накреслень і спільні inline-стилі розташовані перед великим SEO/JSON-LD блоком. Не переносити їх після структурованих даних. Не вбудовувати шрифти в кожен HTML без парного вимірювання холодного й теплого переходу: це збільшує документ і втрачає повторне використання кешу шрифтів.
- Збірка створює піднабори шрифтів з усіх HTML/CSS/JS, включно з HTML entities, Unicode/CSS escapes і динамічними текстами банера, галереї та помилок. Додатково зберігає повну українську абетку й ASCII. Не генерувати піднабір лише з видимого першого екрана. Поточний бюджет двох WOFF2 — 26 000 байтів; збільшення потребує повторного вимірювання швидкодії. Оригінальні TTF і WOFF2 та ліцензія залишаються доступними для старого HTML/CSS.
- Згенеровані WOFF2 не містять TrueType hinting bytecode; контури, advance widths, shaping/кернінг і всі потрібні гліфи зберігаються. Після змін шрифту перевіряти геометрію та читабельність на малих розмірах і різних DPR; не прибирати GPOS/GSUB або підміняти накреслення заради розміру файлу.
- Контролер аналітики вбудовується без зміни логіки на початку body: він має бачити document.body і свій data-measurement-id до появи основного контенту. Не повертати залежність появи банера від зовнішнього JS-запиту. Зберігати відмову, згоду, відкликання, повторне відкриття та відсутність GA4 до згоди.
- Контраст звичайного тексту — щонайменше 4,5:1, великого — 3:1. Перевіряти також hover, focus, дрібні підписи й повідомлення.
- Зберігати клавіатурну навігацію, видимий фокус, семантичні назви, Escape та повернення фокуса після діалогу. Важливий контент і звичайні посилання доступні без виконання JavaScript.
- Зміни shared CSS перевіряти на всіх опублікованих проєктах обома мовами, на 390/768/1440 px. Знімки та автоматичні геометричні перевірки не замінюють оцінки змісту зображень.

## Ресурси та кеш

- Збірка додає content hash у query-параметр v для медіа, шрифтів і CSS/JS. CSS/JS хешуються після версіонування вкладених ресурсів. Не створювати посилання динамічним складанням частин імені файла.
- Зберігати шляхи ресурсів, які можуть використовуватися старим HTML. Видалення або перейменування потребує перевірки перехідного періоду, тривалості кешу та відкату. Старі TTF тимчасово зберігаються для попередніх HTML/CSS.
- Версії в URL забезпечують оновлення браузера. Вони не є сховищем історичних версій вмісту. Річний immutable не вмикати, доки немає гарантованого зберігання відповідних історичних ресурсів.
- Browser TTL і edge TTL перевіряти окремо; HIT Cloudflare не підтверджує довгий браузерний кеш.
- Cloudflare змінювати тільки після мерджу цього PR, успішного Pages deployment і живої перевірки версій ресурсів. Не застосовувати довгий TTL до HTML або project-catalog.json. Конкретний післямерджевий порядок наведено нижче.

## Дані та інструменти агентів

- Звичайні HTML-посилання, описові якорі та доступна галерея — основний інтерфейс. Не приховувати важливий зміст за агентним API.
- project-catalog.json і llms.txt генеруються з фінальних карток і сторінок. Не підтримувати паралельні вручну переписані описи чи окремі непідтверджені факти для агентів.
- Labels, статус, площа та рішення у відповіді інструмента мають відповідати видимому кейсу. Тільки прямі докази дозволяють назвати автоматизацію встановленою; пропозицію й потенціал передавати в їхньому опублікованому формулюванні.
- Поточні search_projects, get_project_details та get_contact_options читають публічні дані. Не додавати неявного надсилання повідомлень, заявок, згоди на аналітику чи інших побічних дій.
- Новий інструмент має одну зрозумілу функцію, схему входу, перевірку параметрів у коді, зрозумілі помилки, коректний результат без збігів і перевірку повторних викликів.
- Перевіряти чинну документацію WebMCP перед зміною інтеграції: API експериментальний. document.modelContext є поточною поверхнею; navigator.modelContext підтримує попередні trial-реалізації. Без API сайт працює звичайно й не завантажує агентний каталог.
- Наявність JavaScript-адаптера або unit-тестів не доводить реєстрацію інструментів у браузері відвідувача. Native WebMCP перевіряти окремо в сумісному браузері; потребу origin trial вирішувати окремо.
- llms.txt — допоміжний путівник; він не замінює robots, noindex чи згоду на використання даних і не гарантує появи в AI-пошуку. ARD-маніфест додавати лише для реального ресурсу після перевірки актуальної специфікації.

### Discovery та Origin Trial

- Збірка публікує `.well-known/ard.json` і сумісний `.well-known/ai-catalog.json` з одного джерела. На сторінках із WebMCP є відповідні `rel="ard"` і `rel="ai-catalog"`. Чинна ARD-пропозиція використовує перший шлях; Lighthouse 13.5.0 ще читає другий. Не підтримувати два незалежно відредаговані маніфести й не прибирати сумісність без перевірки нової версії Lighthouse.
- Запис описує реальний публічний ресурс `agent-skills/piskor-portfolio/SKILL.md`: пошук кейсів, читання підтверджених фактів, секцій і контактів, звичайна навігація без WebMCP. Його джерело — `agent-resources/piskor-portfolio/SKILL.md`. Список можливостей має відповідати фактично зареєстрованим інструментам. Не називати браузерний WebMCP адаптер віддаленим MCP-сервером і не вигадувати endpoint для викликів.
- `npm run test:discovery` після збірки перевіряє актуальну закріплену ARD-схему, conformance поточного Lighthouse, реальні цільові файли й JSON Schema інструментів. Схема, її upstream commit і ліцензія зберігаються в `scripts/schemas/`; вони не є публічним контентом. Після оновлення залежностей або пропозиції ARD повторити обидва валідатори.
- Для production Chrome потребує first-party WebMCP Origin Trial token. Офіційна реєстрація: https://developer.chrome.com/origintrials/#/register_trial/4163014905550602241. Станом на 18.10.2026 випробування активне для Chrome 149–162 до 30.03.2027; строк конкретного токена перевіряти окремо. Користувач надав first-party токен для `https://piskor.com.ua:443`, feature `WebMCP`, expiry `2027-03-30T00:00:00Z`, без third-party matching і субдоменів. Активацію та підпис перевіряти в Chrome на живому домені після deployment.
- Публічний токен записувати в `webmcp_origin_trial_token` у `_config.yml`; метатег з'являється перед `agent-tools.js` на тих самих сторінках. Порожнє значення не створює фіктивного метатега. Використовувати лише origin `https://piskor.com.ua`, без third-party matching чи всіх субдоменів. Не використовувати тестовий або чужий токен.
- Збірка перевіряє origin, feature, формат і строк токена; його криптографічний підпис та активацію підтверджує Chrome. Періодичний CI виявляє прострочення. До завершення строку поновити токен в тому самому процесі PR або прибрати його й залишити звичайну навігацію. Успішний тест із браузерним прапорцем не доводить активації production Origin Trial.
- Маніфести й skill не preload-ити і не запитувати при звичайному відкритті сторінки. JSON каталогу завантажується лише під час виклику відповідного інструмента. Після релізу перевірити HTTP 200 для обох well-known шляхів і skill, їхній вміст та короткий TTL/перевалідацію; не застосовувати місячний кеш до discovery-документів без версій.
- `WebMCP form coverage` залишається N/A, доки на сторінці немає справжньої форми. Пошук для людей є окремою UX-функцією: додавати його за потреби користування, з доступними підписами й declarative-анотаціями, а не для зміни показника аудиту. Не перетворювати згоду на аналітику або відкриття месенджера на автоматичне надсилання заявки.

### P1 release gate та публічний HTTP MCP

- `scripts/check_agent_api.py --site _site --revision FULL_SHA --out NEW_DIR` звіряє JSON з актуальними картками/кейсами, schema та API links, обидві мови/секційні якорі, exact skill bytes/digest, ARD parity й Origin Trial metadata. Кількості беруться з поточного artifact, не з фіксованих 46/92. За 30 днів до expiry CI повідомляє про поновлення; прострочення блокує перевірку. Підпис і реальну активацію WebMCP доводить native Chrome.
- P1 перевірка production: той самий gate із `--live`; зберігати нову папку доказів, GET/HEAD/MIME/byte parity, runtime revision/no-store та failures. Генерувати очікувані publications з фактичного matching Pages artifact. Redirect, timeout і stale data — невдалі спостереження, без прихованих повторів.
- `npm run test:mcp` перевіряє негативні transport/protocol сценарії й сумісний офіційний SDK через справжнє локальне TCP-з'єднання. Це локальний доказ, не підтвердження production. Після активації виконати `node scripts/check-http-mcp.mjs --site ACTUAL_SITE --expected-revision FULL_SHA --out NEW_DIR`, усі три native WebMCP виклики і зовнішній isitagentready зі збереженим складом checks.
- MCP `/mcp` є анонімним читанням уже публічних даних; жодних повідомлень, запису, приватних файлів або неявної зміни consent. Default language uk, explicit en, full-text search охоплює тексти секцій; API та WebMCP мають однакові межі JSON Schema, включно з Unicode. Реєстрація WebMCP одноразова для document; дані ліниві, failed fetch допускає retry.
- Server Card, MCP guide і розширений runtime API catalog активуються атомарно із сервером у matching Worker. Pages зберігає власний статичний каталог GET; не копіювати runtime discovery до статичного origin або не рекламувати неактивний endpoint. Поточна картка Final extension містить identity/transport/versions, а не tools/capabilities. Pin schema/provenance/license у `scripts/schemas/`; точні tools читаються через реальний tools/list.
- Tool invocations HTTP MCP обмежені built-in Rate Limiting binding за [контрактом](public-http-mcp.md#rate-limiting-та-активація): спільний ліміт 120/60 секунд у кожній Cloudflare location, без visitor/IP keys. Після активації перевіряти binding і справжні виклики; 429/503 не маскувати pass. Локальні denied/error fixtures не доводять production saturation або глобальний захист.
- Після кожного релізу bundle Worker оновлюється з matching artifact, навіть якщо змінився лише контент. Зберігати source/data/publication SHA, повний git revision, quota fail-open, asset bypass, logs/preview OFF і доступ Wrangler у раніше погодженому обсязі. Не змінювати DNS, TTL, noindex або політику crawler без відповідного доручення. Недоступність MCP при вичерпаній Worker quota фіксувати як failure; HTML має продовжити працювати через fail-open.

## Валідація та докази

- Встановити requirements-build.txt, виконати python3 scripts/build-site.py, node --test scripts/test-agent-tools.js та git diff --check.
- Збірка перевіряє весь каталог і мовні пари, розміри та srcset, eager/lazy, хеші ресурсів, контраст, JSON-LD, SEO й noindex. Браузерну матрицю виконувати за scripts/check-portfolio-grid.js.
- Після кожної зміни швидкодії перевіряти на production регресійну вибірку з 10 різних URL сторінок: обов’язково `/`, `/en/`, `/portfolio/`, `/en/portfolio/`, два річні каталоги й чотири кейси різних років/типів у двох мовах. Якорі головної не рахувати окремими сторінками: додатково пройти всі пункти меню «Підхід», «Напрями», «Портфоліо», «Контакти» та відповідні EN-переходи. Перевіряти mobile/desktop, завантаження медіа, посилання й мовні пари, консоль/HTTP-помилки, noindex та агентні інструменти. Зберігати FCP/LCP/Speed Index/CLS/TBT і Agentic Browsing. Вибірка не звужує обов’язкових вимог до решти сторінок і не замінює приймання нових або змінених URL.
- Чинна вибірка — `scripts/release-sample.json`; при зміні меню додавати його основні сторінки й актуалізувати решту вибірки. Лабораторний запуск: `node scripts/audit-release-sample.cjs https://piskor.com.ua --output output/release-sample`. Для `/portfolio/` він також зберігає trace і DevTools log для розбору критичного шляху. Він не замінює ручне проходження меню, візуальну перевірку, галерею та native WebMCP.
- Для продуктивності порівнювати щонайменше три прогони з однаковими Lighthouse, viewport, throttling, станом consent і холодним кешем. Зберігати медіану та розкид. Оцінки економії Lighthouse не підсумовувати.
- Порогові вимірювання виконувати з холодним браузерним кешем і банером першого візиту; окремо фіксувати стан CDN-кешу. Звітувати весь діапазон FCP/LCP/SI, а також CLS/TBT. Локальний сервер зі стисненням scripts/serve-benchmark.py та HTTP/1.1 keep-alive потрібен для порівняння доставки тексту; HTTP/1.0 додає окремі TCP-з’єднання й може спотворити вибір ресурсів. Навіть HTTP/1.1 localhost не відтворює HTTP/3 і часовий порядок CDN; результат без CDN/HTTPS не оголошувати production PSI. Окремо перевіряти теплий перехід і збережений вибір аналітики. Не приховувати банер, текст або зображення заради метрики.
- Перед парним бенчмарком перевірити, що кожен URL повертає байти саме своєї збірки: зайнятий порт може залишити старий сервер. Не запускати одночасно інший Lighthouse, збірку зображень або браузерну матрицю. Зберігати також викиди TBT і джерела довгих завдань, не вилучати невигідні прогони.
- Для приймання кожної нової або зміненої сторінки зберігати щонайменше п’ять послідовних публічних PageSpeed-звітів після релізу **окремо для mobile й desktop**. Після зміни спільних шаблонів, стилів, шрифтів чи доставки ресурсів охоплювати всі зачеплені маршрути; твердження про виконання вимоги всім сайтом потребує доказів для кожного публічного HTML-маршруту, включно з обома мовами та службовими сторінками. Фіксувати точні мілісекунди, URL, версію Lighthouse, пристрій, throttling, стан consent і весь діапазон. У кожному прогоні діє загальний контракт **FCP <1000 мс, LCP <1000 мс, SI <1000 мс** та всі застосовні Agentic Browsing аудити (поточний контракт — 5/5). Якщо замовник установив проміжні межі для конкретної серії URL, у звіті окремо позначати і їх, і ціль <1000 мс. Один найкращий прогін, медіана, вибірка 10 URL або Performance 100 не підтверджують стабільність усіх сторінок. Зберігати перевищення й невдалі прогони; додаткові контрольні запуски не замінюють початкової серії. Неперевірені сторінки позначати неперевіреними. Це лабораторна повторюваність, не гарантія для всіх мереж і пристроїв або CrUX.
- Для погодженої мобільної серії історичні 39 URL у `scripts/mobile-si-target-routes.json` мають baseline `5e3652e`; п’ять додаткових PSI failures мають окремий baseline і джерела в `scripts/mobile-si-followup-routes.json`. Для обох когорт діє проміжна межа **FCP <1000 мс, LCP <1500 мс, SI <1500 мс** та окремий звіт про проходження цілі <1000 мс. Перевіряти кожен URL зі списку; production-стабільність підтверджують п’ять послідовних звітів для кожного mobile-URL. Не переписувати історичний 39-URL baseline як нове PSI спостереження.
- Окремо перевіряти перший візит, відмову, згоду й відкликання аналітики та всі реально підключені трекери. Не додавати трекери й preconnect до них до згоди через оптимізацію швидкості.
- Агентний маршрут: знайти кейс, звірити опублікований статус, перейти до секції, перемкнути мову того самого кейсу, відкрити/закрити галерею та знайти контакти. Надсилання повідомлення не входить у цей маршрут.
- Локальна лабораторна оцінка не є production або CrUX-доказом. TBT не замінює INP. Agentic Browsing pass ratio не є оцінкою видимості в AI-пошуку.
- Зберігати noindex,nofollow до окремого явного дозволу. Підвищення SEO-балу не є дозволом на індексацію, PR — дозволом на merge, а успішний build — підтвердженням deployment.

## Після мерджу: Cloudflare

- Дочекатися Deploy Pages для merge commit. Перевірити UA/EN, CSS/JS, WOFF2, обкладинки, llms.txt, project-catalog.json і noindex на живому домені.
- Переконатися, що Cache Rules враховують повний query string, зокрема v. Не ігнорувати його в cache key.
- Browser TTL застосовувати лише до статичних медіа/шрифтів/CSS/JS з версіонованими URL. Користувач 16.10.2026 збільшив його до місяця (фактичний max-age=2678400); не повертати добу під час наступного релізу. Перевірити зміну v після нового вмісту та перехід зі старого HTML. Річний immutable потребує окремого обґрунтування зберігання історичних ресурсів.
- Зберігати короткий TTL/перевалідацію HTML, robots, sitemap, llms.txt та project-catalog.json. Не кешувати весь сайт правилом Cache Everything заради бала.
- Якщо ввімкнено короткий edge-кеш загальних каталогів, обмежувати його GET без query string для `/portfolio/` та `/en/portfolio/` на основному домені. Edge має використовувати Cache-Control origin і обходити кеш без цього заголовка; browser TTL — Respect origin TTL. Поточний origin max-age=600 не підміняти місяцем чи примусовими двома годинами. Після кожного Deploy Pages й перед перевіркою публікації виконати цільовий purge цих двох URL, перевірити новий HTML та повторний HIT з коротким Age. Не включати в це правило кейси, discovery, каталоги даних або невідомі URL; за проблем зі свіжістю вимкнути саме це правило.
- Для загальних каталогів після публікації можна порівняти Compression Rule з пріоритетом Brotli та запасним Gzip з поточним Zstandard. Обмеження — той самий host, точні два шляхи без query і `text/html`; шрифти/зображення/дані не включати. Підтвердити Content-Encoding, розмір передачі та однаковий розпакований HTML; зберігати правило лише за виміряної користі. Це окрема зміна від Cache Rule. Не вимикати аналітику, згоду чи перевірки безпеки заради бала.
- Перевірити реальні Cache-Control, CF-Cache-Status, холодний/теплий запит і післярелізний PageSpeed. За регресії повернути попередні Cache Rules.
- Збільшувати TTL далі лише після підтвердженого зберігання старих URL та перевіреного відкату. Підготовка коду не змінює поточних налаштувань Cloudflare.

## 3. Технічні обмеження і варіанти рішень

- За [документацією GitHub](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages), GitHub Free підтримує Pages з публічних репозиторіїв. Для приватного репозиторію цієї організації потрібен GitHub Team або відповідний Enterprise тариф. Оплата чи зміна тарифу не виконувалася.
- Безкоштовна альтернатива для обговорення: приватний репозиторій вихідного проєкту і окремий публічний репозиторій лише з готовими файлами сайту. Це змінює запитану схему репозиторіїв і потребує окремого рішення щодо доступу для публікації та захисту приватного `main` на доступному тарифі.
- Приховати шаблони, конфігурацію та історію Git можливо; приховати HTML/CSS/JavaScript і медіа, які отримує браузер публічного сайту, неможливо.
- [Вбудований набір GitHub Pages](https://pages.github.com/versions/) наразі містить Jekyll 3.10.0 і `github-pages` 232. [Офіційний сайт Jekyll](https://jekyllrb.com/docs/github-pages/) наразі позначає версію 4.4.1.
- [Власна збірка GitHub Actions](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages) дозволяє збирати Jekyll актуальної стабільної версії та публікувати готовий результат у Pages. Замовник погодив саме цей підхід (Q23).
- GitHub Pages є статичним хостингом. Доставка заявок, CRM, вкладення, календар чи інші серверні функції потребують визначеного зовнішнього сервісу, якщо ці можливості входять до обсягу.
- [Google пояснює](https://developers.google.com/speed/docs/insights/v5/about), що оцінки PageSpeed коливаються між запусками, а польові дані залежать від достатнього обсягу реального трафіку. Ціль 100 зберігається; потрібно погодити методику приймання, перелік сторінок і допустиму повторну перевірку.
- Перевірки швидкості завантаження не замінюють перевірку плавності анімації під час прокручування на реальних пристроях.
- Потрібно визначити, які PR вже дозволені для автоматичного злиття. Обов'язкове схвалення власних PR тим самим обліковим записом створює окреме обмеження GitHub; політика не повинна блокувати єдиного власника або автоматично довіряти стороннім PR.

### SEO та просування

- S01: пріоритетні запити для кожного напряму й ринку; конкуренти; баланс брендового, локального та міжнародного пошуку.
- S02: поточний стан `piskor.com.ua`, власник домену, існуючий сайт/індексація/посилання, майбутнє підключення домену й перенесення старих адрес.
- S03: початкова адреса GitHub не індексується; індексацію ввімкнути після фіналізації й підключення власного домену (Q17, BL-003). Відрізняти цю вимогу від приватного доступу: репозиторій і опублікований попередній перегляд залишаються публічними.
- S04: UA/EN URL, canonical, hreflang, sitemap, robots, метадані й соціальні прев'ю; стабільні адреси кейсів.
- S05: структуровані дані лише на підставі підтверджених відомостей; Google Business Profile, Search Console та аналітика.

- S07: дослідження запитів/конкурентів і контент-план обов'язкові після запуску (Q22, BL-004). Публікації, рекламні кампанії, їх бюджет, строки та метрики успіху деталізуються на тому етапі; зараз їх не запускати.

### Якість, безпека та експлуатація

- T01: погоджено актуальний стабільний Jekyll через Actions (Q23); версії й сумісність залежностей повторно перевірити перед установленням.
- T02: модель репозиторіїв, права організації/користувачів/ботів, захист `main`, початкове створення гілки, правила для сторонніх PR.
- T03: перелік обов'язкових CI перевірок: збірка, форматування, посилання, переклади, SEO, доступність, браузерні сценарії, швидкість, безпека залежностей/коду/секретів/workflow.
- T04: правила auto-merge після перевірок; актуальність перевіреного коміту, Conventional PR title, squash title + body, changelog/release cadence.
- T05: щоденний розклад сканів і перевірки оновлень, часовий пояс, одержувач сповіщень про проблеми, реакція на вразливості; окремо визначити поводження з несумісними великими оновленнями.
- T06: методика PageSpeed — категорії, усі/репрезентативні сторінки, обидві мови, кількість повторів, реальна URL після публікації, критерії блокування PR і критерії фінального приймання.
- T07: бюджет зображень, шрифтів і JavaScript; окремі виміри плавності прокручування, підтримувані браузери, пристрої та слабкий зв'язок.
- T08: спосіб попереднього перегляду до публікації, візуальне погодження, повернення попередньої версії, сповіщення про невдале розгортання та перевірка опублікованого сайту.

## 6. Коли бриф можна вважати завершеним

- Кожна тема має відповідь, погоджене типове рішення або явно відкладений обсяг із відповідальним.
- Узгоджені карта сайту, головна конверсія, контент для запуску, сценарій анімації та візуальний напрям.
- Підтверджені актуальні факти студії та право публікувати матеріали.
- Погоджені приватність, витрати на сервіси, схема Pages, дозволи на auto-merge й політика оновлень.
- Нефункціональні вимоги мають вимірювані критерії приймання, включно з PageSpeed, анімацією, доступністю, безпекою та публікацією.
- Визначені обсяг SEO робіт до запуску й після запуску, доступи та власник регулярного контенту.
- На основі відповідей підготовлено остаточне ТЗ та послідовність реалізації; цей чернетковий реєстр сам по собі не означає завершення збору вимог.
